# Content Tracking Dashboard — Project Instructions

## Overview
Personal media analytics dashboard: analyzes ~370 titles (movies/series) logged in **Postgres** — Netlify Database, the managed Postgres that ships with the platform. Frontend is a vanilla JS SPA; Netlify functions query the database directly with `pg`. There is **no Apps Script** anywhere — nothing to redeploy by hand. The Google Sheet it was migrated from is retired; `admin-import.js` and `lib/sheets.js` exist only for that one-time import and are deleted together once it is confirmed.

## Tech Stack
- Frontend: `index.html` (static shell + nav) + `app.js` (SPA that renders every page from the Sheet API) + `styles.css`
- Charts: Chart.js 4.4.1 (CDN, loaded on every page even though only Current Year / All Time use it)
- Backend: `netlify/functions/` — `watchlist.js` (data + goal read), `goal.js`, `suggestions.js`, `admin-login.js`, `admin-entry.js` (create/update/delete, by entry id, plus the cleanup scan's read), `admin-import.js` (the one-shot Sheet import), `tmdb-search.js` (TMDB search + OMDb rating/imdbId), `calendar.js` (release calendar: TMDB films + TVmaze episodes), shared code in `netlify/functions/lib/` (`db.js` — Postgres, `session.js` — admin cookie, `throttle.js`, plus `sheets.js` while the import still needs it)
- Data store: Netlify Database — schema as a committed migration under `netlify/database/migrations/`, applied by the deploy (before a production publish; on every deploy preview, which gets its **own database branch seeded from production**). `NETLIFY_DB_URL` is the connection string Netlify injects per context; `package.json` (dependencies only — `@netlify/database` and `pg`) is what makes Netlify provision the database at all
- Release data: TMDB (`TMDB_API_KEY`, already configured on Netlify) for films, **TVmaze** for episodes — a free public API that needs no key at all. Nothing new has to be configured for the Calendar page on the deployed site, but the key is per **environment**: Netlify holds a value per deploy context (production / branch deploys / deploy previews / local development) and a value set for production only is absent everywhere else, so `calendar.js` reads the key per request and its warning **names the environment it was missing from** (`CONTEXT`, or "no Netlify context — local run"). A local function runner has no Netlify environment at all unless it is given one, which is why a locally served Calendar can be film-less while production is fine.
- Hosting: Netlify; dark mode persisted in `localStorage` (`ct-theme`)

## Files
```
index.html   → static shell: loading screen, nav tabs (Readme/Current Year/All Time/Data/Timeline/Calendar/Random Pick/Submit), theme toggle
app.js       → SPA: data fetch + all page/template rendering (uses many emojis as decorative icons)
styles.css   → design tokens in :root + html.dark; responsive blocks at ≤900px and ≤600px
netlify/database/     → migrations, applied by the deploy (0001_init.sql: entries, suggestions, settings)
package.json          → dependencies only (no scripts): @netlify/database + pg
netlify/functions/    → the API listed above
```

## Code Style / Conventions
- Nav tabs carry inline 13px SVGs declared in `index.html`; the brand mark is an inline TV SVG. On ≤900px the tab icons are hidden and `.nav-tabs` becomes a scrolling strip with a mask fade — the single-row nav is wider than the viewport between 601px and ~850px otherwise.
- `--nav-h` must match the **measured** nav height at each breakpoint (60px desktop, 73px mobile) — the sticky table header, timeline jump bar and month headers all offset from it.
- The theme toggle shows two SVGs (`.icon-sun`/`.icon-moon`) toggled by `app.js`; **do not** switch it back to `textContent = '🌙'/'☀️'`.
- The app body uses many emojis as icons (media-type emojis, insight rows, poster placeholders). Standardizing onto a real icon library is a known, feasible refactor — be careful: `app.js` frequently rewrites these nodes.
- "Recently Watched" cards, the Data table and the Random Pick result all pull real posters through the shared `MEDIA_CACHE` / `loadPoster` / `loadVisiblePosters` path; the emoji fallback is only for titles the media API can't resolve, and it swaps the `<img>` for a `<span class="… placeholder">`.
- **Display-level normalization only** — the store keeps whatever was typed (the Sheet did, and the rows imported from it still do). `GENRE_MAP`/`TYPE_MAP`/`smartCaseName` in `app.js` merge near-duplicate labels ("Science Fiction" → "Sci-Fi", "Series/Show" → "Series") and capitalise all-lowercase titles at render time.
- Year-over-year figures compare **the same months** on both sides (`Jan–Sep 2026` vs `Jan–Sep 2025`), skipping a month that is still running; the full previous year appears as context only. Don't reintroduce year-to-date vs full-year comparisons.
- Ratings come from the on-demand media lookup and are cached per device: the Data page shows coverage and offers "Load all ratings" (concurrency 3), and `buildDataCSV` falls back to `cachedRating()` so the export isn't limited to rows on screen.
- `ct-media-cache` stores `{ items, miss }`. A title the media API answers **without a rating** is recorded in `miss` (7-day TTL, `MEDIA_MISS_TTL`), because such a title never gains an `imdbId` and would otherwise be re-queried — TMDB *and* OMDb — on every single re-render. `ratingCoverage().dead` counts those as "unavailable" so the coverage readout and the "Load all ratings" button can actually finish; a later success clears the marker.
- The Data table's `<th>`s are keyboard-sortable (`tabindex`/`aria-sort`/`title`); sort state lives in `sortDataBy()`, which also restores focus to the same header (the re-render throws the element away). `dataVal()` must return `''` for a missing value — `compareData()` sinks empty values to the bottom, but a numeric `0` is not empty, so returning 0 for a missing episode count / rating buried the 92 movies (or every unrated row) at the top of an ascending sort.
- `#dat-table` owns the horizontal scrollport at ≤900px too, not just ≤600px: the 9-column table is ~915px wide, so between 601px and ~950px the body's `overflow-x: hidden` used to clip the Rating / Watch Date columns with no way to reach them. The sticky header therefore only sticks where the table fits without scrolling (≥951px).
- Every `history.replaceState` writes `location.pathname` before the query. A **fragment-only** URL (`'#data'`) keeps the *current* query string, which left cleared filters in the address bar and let `applyDataFilters()` resurrect them on the next render — and left a one-shot `?fresh=` marker behind.
- **Never put `overflow: hidden` back on `table`** — it traps the sticky header/name cells in a box that never scrolls. The rounded corners are painted per-cell instead (thead th first/last, last row's first/last td).
- Timeline: `bindTimelineNav()` wires the year jump bar and the per-month expanders; long months render collapsed after 5 items.
- The database layer (`lib/db.js`) is the only place that knows the schema, and it keeps the **wire shape the page already consumes**: a row goes out as `{ _row, Name, Season, Type, 'Details/Genre', Platform, 'Episode Count', Screentime, 'Watch Date', Month, Year }`, so the frontend needed no change for the move. `_row` is a row's `id` now rather than its sheet row number — the page only ever hands it back, and an id does not shift when a row above it is deleted, which is strictly better than what it replaced. Dates are stored as `DATE` and read back as ISO; the display date ("3-Sep-26") and the Month/Year pair are derived in `toWireRow()`.
- The duplicate rule is implemented once, in `lib/db.js` (`seasonKey` — "S2"/"Season 2"/"2" — plus case-folded name, watch date and screentime), and `createEntry()` does its check and insert inside one transaction holding an **advisory lock on the title**, so two adds arriving together cannot both pass the check. `admin-entry.js` reports the existing id as `{ duplicate: true }` exactly as before.
- Admin endpoints share `lib/session.js`'s `validSession()`; a write that matches no row answers 404 `ENTRY_MISSING` instead of reporting a success that did not happen (a sheet row number could not miss).
- The Admin page's **Database Cleanup** card exists because the rest of the site cannot show its rows: `mapRows` drops every row whose year reads as 0, so a row with no watch date and 0 screentime (a blank import row, an abandoned add) is in no list, chart or search — the edit search cannot reach it either. The scan (`{ action: 'invalid' }` on `admin-entry`, `listInvalidEntries()` in `lib/db.js`) reads the table directly, ids and timestamps included, and each listed row is deleted with the same verified single-row delete; the row leaves the list in place because nothing else on the page was showing it. The card's table opts out of the app's global table styling explicitly, and the ≤900px column rules that used to match any table are scoped to `#dat-table` — a new table brings its own styling.
- Deploy previews get a **database branch seeded with a copy of production data**, so a preview shows real watch history and its schema changes cannot reach production. Anything exercised on a preview is exercised against real rows — do not treat a preview as a sandbox for data.
- Adding a title through the Admin form is **gated by a duplicate check before any request is sent** (`submitAdminEntry()` → `adminDuplicateCheck()`), matching on the same keys the Duplicate Checker uses — `dupNormTitle`/`dupKind`/`dupSeasonKey`/`dupDateKey`, so "S2"/"Season 2"/"2" agree, casing never hides a match and a movie never collides with a same-named series. An exact repeat (same watch date *and* screentime) is refused with no way through; the same title+season on another date stops too but offers "Add anyway", the deliberate rewatch override — the same call the Duplicate Checker makes when it lists these as review-only. The gate fetches the watchlist when it has not been read yet and **stops the add if it still cannot be read**, rather than writing unchecked; use `loadData(true)` there so the repaint cannot wipe the form. The server-side rule (`createEntry()`'s check inside the locked transaction) stays as the last-resort guard against a double submit.
- Data loads from the deployed functions at runtime, so a bare static server serves the shell but returns 404 for data — expected without the backend. The database is not part of the frontend: nothing in `app.js` talks to Postgres, and no connection string belongs in the browser.
- The **Release Calendar** is the one page whose data does not come from the Sheet. Films come from TMDB `/discover/movie` (a release-date window in one region, plus one `with_watch_providers` sweep per platform on the Sheet's own list — see the platform bullet below), episodes from TVmaze `/schedule/full`. It must be that TVmaze endpoint: the plain `/schedule` one excludes "episodes from global Web Channels like Netflix", i.e. exactly the half a release calendar is for, and `/schedule/full` answers with every future episode in a single ~3.3 MB request. TMDB cannot serve a calendar of episodes at all — its TV discover answers with *shows* that have an episode in the window — so this split is deliberate, not incidental. Both halves are best-effort: if one source fails the other still renders and the response carries `warnings` the page shows.
- `_headers` must keep `https://static.tvmaze.com` in `img-src`. The episode half of the calendar paints TVmaze posters; without that host they silently fall back to the emoji placeholder and read as missing data (same trap the note above the CSP block describes for `image.tmdb.org`).
- The calendar's filters open at their **widest** — Everything, Films & TV, All platforms, All regions — because that is the view that needs no explaining: what is out, everywhere, on the services the watchlist logs. Everything is genuinely noisy (counted with the daily strips, TVmaze lists ~300 entries a day), which is why a month's cells preview the notable few rather than the first few and **New & notable** stays one select away for a month that reads better thinned. The Show select's other option, **Episode releases**, is the readable middle — every episode of every show on its release day, with the films and the strips that air daily left out. Those strips are detected in `calIndex` rather than named: a title TVmaze calls news/talk, or one whose episodes land on more than a third of the window's days (`CAL_DAILY_FLOOR` is the floor, so a one-day window cannot flag everything; a fixed count would flag every weekly show across a year). A premiere, a search query or **a chosen platform** bypasses the rule — typing the title, or picking CBS, *is* the request for it, so that platform's own episodes come through while its nightly strip still does not — and `calSyncTypeSelect()` disables the Type select's "Films only" option while the scope is on, because the pair can only ever paint an empty month. "Everything" is one select away, and the day drawer lists the whole day with sticky tier headings and a "Show all N" button that ignores the page filters for that day. A **day cell previews the notable few, not the first few**, and not one kind's first few: `calPreview` gives the day's most popular film the first slot, its best premiere the second, then the strongest of what is left — so a Friday leads with the film that actually opens and the shows around it, instead of three premiers nobody has heard of. Films below `CAL_FILM_FLOOR` (TMDB popularity 5) take no slot at all rather than crowd out shows on a quiet Saturday, and are only shown when the day has nothing else. Ordering inside a slot is `calTrend`, whose popularity term is a **per-kind percentile** (`calPopularity`), because the two sources' figures are not one scale — TVmaze's show weight saturates (38 different shows share a 100 in one October) while TMDB's popularity has a long tail (median 3) — so a raw score ranks TVmaze against itself and buries a theatrical opening under a PBS cooking show. The cell's count and "+N more" stay about the whole filtered day (the button counts what the cell is *not* showing), and the drawer behind it is the complete day — the one place the month's noise dial (`calDayView`) is switched off. Counts read as what is actually in the view (`calCountParts`): no "0 films" beside episodes, and the zeros only when nothing matched. Past days of the current month are dimmed and deliberately empty — it is a release calendar, not a history page.
- The calendar **rolls on the clock**: `calYearMonths()` is every month from the current one to December (a month that has ended can only be empty, so it is never offered), the two scope tabs carry the current and next year, and nothing in that chain is fixed at build time. The **window is the view**: this year asks for one month at a time (the current month from today, a later month whole) and next year asks for the whole year in one request — a different kind of window, which is why the two scopes are separate windows rather than one long one. Loaded windows are cached by `from|to|region` in `calState.cache` (max 4, pruned when the clock makes an entry obsolete), so moving between months repaints instead of refetching, and a stale copy paints immediately while the refresh lands behind it. `calScopeWindow()` is the single definition of "what am I asking for" — add a scope there, not at a call site.
- Auto-update is `calStartAuto()`/`calStopAuto()`: a minute tick (`calTick`) notices midnight and rolls the page forward — today's marker moves, the ended month leaves the strip, 1 January rolls both year tabs — and a 20-minute poll refetches the open window while the tab is visible (`visibilitychange` covers the rest). Timers are torn down in `navigateTo()`, so they cannot accumulate or keep polling from a page nobody is looking at. A *failed background* refresh keeps the window on screen and says so in `calState.notice`; only a failure with nothing to paint becomes an error state. **Refresh** stays the CDN-bypassing `?fresh=` load: the poll reads the CDN's 15-minute copy.
- The region picker's default is **All regions**, and "all" is not a region TMDB has: a film releases country by country and `region` is one ISO code per request, so `region=all` is a sentinel the **page** defines and the function unions over. The page sends the list its own picker offers (`regions=US,GB,…`) — that dropdown is the one place the list exists, and a second copy inside the function could silently drift from it. `requestedRegions()` validates every code, folds case, drops duplicates and caps at `MAX_UNION_REGIONS` (30); a missing or unusable value falls back to `US` exactly as before. The function then runs the ordinary region pipeline once per region and merges the results, so a union is ~10 upstream calls per region (~250 for all 24) in one request — which is why it has its own wall-clock budget (`UNION_BUDGET_MS`) and its own region concurrency (`UNION_BATCH`, multiplied by the per-region `BATCH` for the real ceiling; TMDB's documented upper limit is "somewhere in the 40 requests per second range", and three regions at a time is already ~15 requests in flight, so more only buys 429s). Past the budget the regions that did not get their turn are **named in the warning**, the cinema pages already fetched are still returned, and the response is cached `max-age=60` instead of 900 so the next load retries — `films.complete` (set by `loadMovies`) is what the handler switches the header on. A single-region request is unchanged, budget included.
- The films come from `/discover/movie` with **`region` + `release_date.gte/lte` + `with_release_type`**, never with `primary_release_date.*`. That pair is the documented region-aware one; pairing a region with the *primary* date filters leaves the filter global while the date TMDB reports back is the regional one — US, GB and IN returned an identical list, and a window starting today answered with 80 undated titles crammed onto its own first day, none of them the films that actually opened that month. Caught by checking a live deploy against a public October 2026 US schedule (Street Fighter, Whalefall and Sense and Sensibility on 16 October, Clayface and Wildwood on 23 October); `item.release_date` is re-checked against the window on the way in, so a popularity-ordered page can never drag next spring into October.
- The calendar **only fetches from the platforms the watchlist logs against** — `PLATFORMS` in `calendar.js`, with `PLATFORM_SPELLINGS` for the names the two APIs spell differently (TMDB's "Prime Video" and "Max", TVmaze's "Apple TV" and "JioHotstar", TMDB's regional "CBS US" for the watchlist's "CBS"). The comparison is name-without-punctuation, so "Apple TV+" and "Apple TV Plus" are one string; anything else is dropped at the fetch boundary, so the page never receives, counts or offers a title that is not watchable on those services. Two entries on that list are not services: **"Theater"** is a cinema release, which is a property of the film (its theatrical release date, the `2|3` pass) and is appended to the film's `providers` as that label, so the platform filter can ask for cinema releases alone; **"Other"** is how both the Sheet and TVmaze spell "no platform recorded". A film survives only if it is theatrical or on a listed service; an episode only if its network/webChannel canonicalises to a listed platform. `providers[0]` is the service a film arrives on and "Theater" is appended last, so a cinema-only release isn't ranked by the app as a streaming arrival (`CAL_THEATER` in `app.js`).
- The function's film window is sized by its own length (`moviePlan`): the **theatre half** is one query of `2|3`, walked in regional release-date order in chunks of `BATCH` until a page's last entry passes the window or a page comes back short (cap 25 pages — a busy US month really is that deep: 12 pages stopped the walk around the 27th, with 30 October missing) — that early stop is what keeps a month's crowded opening days from eating the budget before the rest of it is reached, and a quiet month stops after one chunk. Beyond 100 days it cannot be listed to the day (date-ordered pages of a year only reach its first weeks), so the same `2|3` types are taken in 3 popularity-ordered pages instead: a year at a glance. The **streaming half is not a query shape at all** — it is one popularity-ordered page per listed platform in that region, and those sweeps both label and **add** films, because a title only on a service is exactly what this calendar is for. Where the two dated the same film (theatrical vs digital) the earlier wins, so a film's day does not depend on which pass reached it last — that rule lives once, in `mergeFilm`, which a union leans on: a film found in nine regions is one entry dated by the earliest of them and carrying their labels (still capped at three), never nine rows. `MAX_DAYS` (400) is what lets the year window through at all — lowering it back under 366 silently truncates next year.
- The calendar **remembers its filters** per device (`ct-cal-filters`, via `calStoredFilters()`/`calSaveFilters()`), so the view it opens with is the one that was actually asked for: a reload after choosing "Episode releases" must not fall back to the default, which reads as a month with nothing in it. The stored blob carries a version (`CAL_FILTERS_VERSION`), bumped when one of the **defaults** changes: storing only ever happens on a deliberate change, so an untouched device has nothing saved and needs no bump, but a device that once stored the *old* default would otherwise keep opening on it and the new default would look unimplemented. The remembered region works the same way (`ct-cal-region`, validated against the picker, defaulting to All regions rather than to the browser's locale). `calFilterFlagHTML()` names the filters that are in force in the summary line for the same reason, and every stored field is validated on the way in — an unknown scope, a corrupt blob or the blank platform a rebuilt `<select>` reads back as all fall back to the default instead of breaking the page.
- The platform filter's options are **the platforms the loaded window holds**, not the ones the current Show/Type selects happen to be showing: there is no minimum count (`CAL_PLATFORM_CAP` only bounds the list) because a floor of eight silently hid CBS, Netflix, Hulu, Disney+ and HBO Max from the whole-year view, where everything is thin. Each candidate is judged through `calMatches(item, { platform: name })` — as though it had been chosen — so an offered option always shows something, and the platform in force is always kept, so a remembered filter is never reset to "All platforms" by a window that happens not to carry it. The kept one is the single exception: paired with a Type select that excludes everything it has (CBS with "Films only"), it stays chosen and the month says nothing matches, which is the honest answer to two filters that contradict each other.
- `calState.platformsKey` is an options cache for the platform `<select>`. **Both `renderCalendar()` and `calAdopt()` must clear it**, because the page render (and every newly painted window) writes a fresh `<select>` holding only "All platforms": without the reset `updateCalendar()` decides the list is already current and leaves the dropdown empty for the rest of the visit. `calMatches()` also treats an empty platform value as `all`, since a select with no options reads back as `''`.
- Twelve month tabs cannot be one row on a phone: the strip **wraps** at ≤900px (a hidden month is a month nobody finds) and scrolls at ≤600px, where `updateCalendar()` scrolls the active tab back into view — the strip keeps its own scroll position across a rebuild otherwise.
- Calendar cell meta (premiere tags + platform) is hidden at ≤900px. Seven columns are ~73px wide at 601px and a nowrap "Series premiere" tag is 81px — it pushed the whole document sideways. Phones get the agenda instead of the grid (≤600px), which keeps its meta and skips empty days; the drawer keeps full detail at every width.
- The calendar response is cached `max-age=900` at the CDN and repainted from the in-page window cache. **Refresh** passes `?fresh=<timestamp>`, a URL the CDN has never seen — the same one-shot marker convention `reloadFresh()` uses after an admin write. The background poll deliberately does *not* pass it (it is meant to read the CDN copy), so a first visit that lands while TMDB is down can keep a film-less calendar for up to 15 minutes unless Refresh is pressed — which is why the partial-load warning is shown rather than swallowed.
- Calendar markup from the two APIs is escaped like any stored value (`escapeHTML` on titles, platforms, episode names and genres), and item links only survive `calSafeUrl()` (http/https).

## Build & Run
- No build step: the repo root is the publish directory. `package.json` exists for dependencies only (and its lockfile is committed, so the driver versions are pinned); Netlify installs them on deploy.
- Serve the folder statically for shell-only work; to exercise real data locally, use a tiny static server that proxies `/.netlify/functions/*` to the deployed site (and delete it afterwards — it is not part of the project).
- The real local run is the Netlify CLI (26+): `netlify link`, `netlify database migrations apply` (migrations are **not** automatic locally), then `netlify dev`, which starts a local Postgres and injects `NETLIFY_DB_URL`.
- Deploys are Netlify; the functions, the static shell and the migrations ship together from `main`. A migration that fails blocks the publish.
